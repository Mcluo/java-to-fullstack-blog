## 问题的起点

最近有个问题让我想了很久：

> 现在后端工程师写业务 Skill，似乎已经不能体现价值了。该怎么办？

这个焦虑并不陌生。当 AI 让"写 Prompt"的门槛越来越低，当 PM、产品、甚至业务同学也能配置出一个可用的 Skill，技术人开始感到自己的位置在被蚕食。

这种感受是真实的。但方向判断错了。

---

## 问题的本质：你在哪一层？

Skill 的本质是：**Prompt + Tool 调用**。

这意味着一个足够聪明的非技术人员，学习一段时间，完全可以写出一个"能跑"的 Skill。既然如此，单纯"写 Skill"确实不是后端工程师的护城河。

但这里有一个关键的追问：**那个 Tool，是谁实现的？**

Skill 之所以能调用数据、能查库、能触发业务流程，是因为背后有一层工具层在支撑。这层工具层，才是后端工程师的主场。

---

## 后端工程师的真正护城河

### 1. 控制 Skill 背后的基础设施

写 MCP Server、实现 Tool、暴露 HSF 接口、设计 API——这些是 Skill 能力的上限。

没有后端工程师实现的 Tool，别人写的 Skill 只是空壳。你不需要比别人更会写 Prompt，你需要让 Prompt 背后有东西可以调。

### 2. 数据质量和系统可靠性

Skill 的输出质量 = 数据质量的上限。

写 Skill 的人不懂数据模型，不懂 SLA，不懂幂等性，不懂脏数据处理。一个"能跑"的 Skill 和一个"可信赖"的 Skill 之间的差距，正是后端工程师的价值所在。

### 3. 复杂业务逻辑的 Agent 编排

简单 Skill = 单轮问答（谁都能写）。

复杂 Workflow = 多 Skill 协作 + 状态管理 + 异常处理 + 幂等保障。这需要软件工程思维，不是 Prompt 工程师能做到的事情。

### 4. 评测和质量体系

这是最容易被忽视、也是最有长期价值的一块。

- 定义 Skill 质量的 Metric
- 自动化测试和回归
- 输出格式评估（Output Format Evaluation）
- A/B 测试不同 Prompt 策略的效果

业务侧根本做不到这些。而没有这些，AI 系统就只是一个玩具，无法上生产。

---

## 重新定义你的角色

| 低价值定位 | 高价值定位 |
|-----------|-----------|
| 写 Skill Prompt | 设计 Skill 执行架构 |
| 调 API | 建 MCP Tool 生态 |
| 跑 Demo | 建评测 + 回归体系 |
| 单 Skill | 多 Agent 编排系统 |

**不要把自己定位为"写 Skill 的人"，而是"让 AI 系统可靠运行的工程师"。**

让别人写 Skill，你控制 Skill 能否正确运行。

---

## 一个具体的检验标准

如果你离开这个团队，AI 系统还能正常运行吗？

- 如果答案是"能"，说明你只是在维护 Prompt，可替代性很高。
- 如果答案是"不能"，说明你控制着某个关键基础设施，这才是你的价值。

---

## 结语

AI 时代对工程师最大的挑战，不是"AI 能不能写代码"，而是**"你有没有意识到自己应该去掌控哪一层"**。

Skill 是入口，Tool 是基础，数据是燃料，评测是保障。后端工程师天然离这四层更近，只是需要主动去占领它们，而不是守着"写 Skill"这件正在被大众化的事情。

方向是：**从 Skill 的生产者，变成 Skill 生态的基础设施建设者**。
