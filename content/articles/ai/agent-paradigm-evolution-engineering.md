# Agent技术范式演进全景：形未变，神已不同

> 本文提炼自ATA高赞文章《Agent核心技术概念与范式发生了哪些演变以及背后的思考》（135赞/134收藏），去水提纯，保留核心逻辑与判断框架。

---

## 一句话结论

Agent的宏观架构（Prompt + Planning + Memory + Tools）三年没变，但每个模块的**内核**都被重构了。统一方向：**从"靠模型智商硬扛"转向"工程化确定性 + 模型不确定性的协作"**。

---

## 四个阶段：Agent自主性的逐步释放

| 阶段 | 时间 | 核心特征 | 局限 |
|------|------|----------|------|
| **被动响应** | 2023 | 单步ReAct，一问一答，3轮推理就到顶 | 短链路，严重依赖用户明确指令 |
| **工作流Agent** | 2024 | 硬编码流程，用工程约束弥补模型弱点 | 机械化，无法动态调整 |
| **自主Agent** | 2025 | 长程规划，自主拆解+多轮迭代+自我校验 | 需要清晰Spec，仍依赖人类设定边界 |
| **自进化Agent** | 2026 | 任务中沉淀经验，越用越好 | 刚起步，机制尚不成熟 |

**关键认知**：四个阶段是**并存互补**，不是替代关系。选哪个取决于场景复杂度和稳定性要求。

## 六大模块的范式重构

### 1. Prompt：从单体小作文 → 动静分离

**早期**：一个Agent一段精心调试的System Prompt，人设+目标+约束+示例全塞进去。场景多了维护崩溃。

**现在**：
- System Prompt只保留**固定的**系统级指令和行为规范
- 动态内容（任务要求、领域知识、人设）拆到外部Markdown文件
- 通过**渐进式披露**按需加载（SKILL.md、USER.md、CLAUDE.md）

**本质**：上下文的组织形式变了——固定骨架 + 文件挂载，实现真正的模块化。

---

### 2. Planning：从提示词技巧 → 模型原生能力

**早期**：靠"Let's think step by step"等提示词引导线性推理，模型推不动就断。

**现在**：
- 模型原生具备结构化分解能力（宏大目标 → 子任务Todo List）
- 多步协同 + 长程推理，保持逻辑一致性
- 可动态实例化子Agent专项解决子问题

**驱动力**：纯粹是底层模型推理能力的升级带来的。Planning从"技巧"变成了"能力"。

---

### 3. Memory：从纯向量检索 → 文件系统化混合管理

**短期记忆**演变：
- 不再简单堆砌历史对话
- 引入阈值压缩、结构化摘要、重点提取
- 保留头尾关键指令，剔除中间噪音

**长期记忆**演变：
- **事项型**（用户偏好、待办）→ 文件系统记录（MEMORY.md、日志文件），比向量检索更可控可读
- **知识型**（领域知识）→ 本地Markdown知识库 + 轻量向量检索混合；企业级仍需专业向量数据库

**本质**：从"全量丢进向量库"回归到"结构化文件 + 精准检索"的混合模式。

---

### 4. Tools：从Function Call → CLI + Script

这是**变化最大**的模块。

**早期痛点**：每个工具都要开发API、写Schema、注册函数。系统没有现成API？那就去"补全"——成本极高。

**现在的范式转移**：

**CLI原生化**：
- `grep`、`curl`、`cat` 这些命令是模型预训练数据的一部分——**先天知识**
- 不需要定义Schema，不需要注册函数
- 不认识的工具？跑 `--help` 自学

**Script脚本化**：
- 工具逻辑封装为独立脚本（Python等）
- 复杂的鉴权、参数拼接隐藏在脚本内部
- Agent只需要知道"调哪个脚本 + 传什么参数"

**核心转变**：从"人为适配模型"转向"利用模型原生能力"。MCP在这个脉络中的定位是协议层优化，标准化了工具注册与发现，但未改变底层逻辑。

---

### 5. Workflow：从刚性编排 → Skill封装 + Workflow兜底

**早期**：固定的状态机，第一步→第二步→第三步，无论环境怎么变都死板执行。

**现在**：
- 逻辑写入Skill的Markdown文件，模型阅读即理解
- 执行通过关联Script进行代码级编排
- 一个复杂流程 = 一个可复用的Skill

**但完全去掉Workflow有风险**：容错率极低的场景仍需确定性边界。

**当前最佳实践**：**Skill为主，Workflow为辅/兜底**的混合架构。

---

### 6. Environment：从无状态 → 有状态运行时

Agent引入文件系统操作和代码执行后，必须有专属Workspace。

两种形态：
- **本地电脑**：便利灵活，但操作失误可能影响用户数据
- **沙箱/容器**：企业级首选，隔离安全，破坏性命令不影响宿主

## 统一逻辑：一张图看懂全部变化

```
早期：模型能力弱 → 重外部约束（大Prompt、硬Workflow、API封装）
现在：模型能力强 → 轻约束重能力（文件加载、原生推理、CLI直调）

不变的原则：
┌─────────────────────────────────────────────┐
│ 工程化确定性（文件系统/CLI/沙箱/Harness）    │
│         ↕ 承载 ↕                             │
│ 模型不确定性（推理/规划/决策/生成）          │
└─────────────────────────────────────────────┘
```

**每个模块的演进都在做同一件事**：把确定性的部分用工程手段固化，把不确定性的部分留给模型发挥。

## 选型指南

```
你的场景需要模型自己决定下一步吗？
├─ 不需要 → Workflow Agent（步骤固定，保质保量）
├─ 部分需要 → 混合架构（Skill + Workflow兜底）
└─ 完全需要 → 自主Agent + 轻量Harness约束
    └─ 还需要跨session经验积累？ → 自进化Agent
```

---

## 带走一句话

> **"通过工程化手段构建确定性，以承载模型不确定性。"**

模型会升级，框架会更新，但这个原则是未来很长一段时间内构建高质量Agent的基石。理解演进背后的逻辑，比追具体工具更重要。
