# 大模型微调入门：概念、原理与技术选型全景图

你已经用上了 ChatGPT、Qwen、Llama 这些大模型，但总觉得它们在你的业务场景下「不够听话」——回答格式不对、专业知识不准、语气风格不符。这时候，**微调（Fine-tuning）** 就是你需要掌握的技能。

<img src="/images/finetuning/pretrain-vs-finetune.svg" alt="Pre-training vs Fine-tuning vs Inference" style="max-width:100%;margin:1.5em 0;" />

## 1. 什么是模型微调？

### 1.1 一句话定义

> 微调 = 在一个已经预训练好的大模型基础上，用你自己的数据继续训练，让模型适应特定任务或领域。

用 Java 的类比：预训练模型就像一个通用的 `BaseService`，微调就是你继承它，然后 `@Override` 部分方法来适配你的业务逻辑。

### 1.2 预训练 vs 微调

| 阶段 | 预训练（Pre-training） | 微调（Fine-tuning） |
|------|----------------------|---------------------|
| 目标 | 学习通用语言能力 | 学习特定任务/领域知识 |
| 数据量 | TB 级互联网文本 | KB~GB 级任务数据 |
| 计算量 | 数千张 GPU，数周~数月 | 1~8 张 GPU，数小时~数天 |
| 成本 | 百万~千万美元 | 几十~几千美元 |
| 谁来做 | OpenAI、阿里、Meta 等大厂 | 你（应用开发者） |

### 1.3 形象比喻

把大模型想象成一个刚从大学毕业的**通才**：

- **预训练** = 大学四年的通识教育（读了海量书籍，啥都懂一点）
- **微调** = 入职后的岗前培训（针对具体岗位，学习公司业务规范）
- **推理** = 正式上班干活

你不需要从幼儿园重新培养一个员工（预训练），只需要对这个「名校毕业生」做短期培训（微调）。

## 2. 为什么需要微调？

### 2.1 通用模型的局限

即使是最强的通用大模型，也有明显短板：

| 问题 | 表现 |
|------|------|
| **格式不可控** | 让它输出 JSON，可能混入 Markdown |
| **领域知识不足** | 你的内部术语、产品名称它不认识 |
| **风格不一致** | 有时正式有时随意，难以保持统一 |
| **幻觉严重** | 对你的业务数据编造事实 |
| **指令遵循差** | 复杂指令经常忽略部分要求 |

### 2.2 微调能解决什么

微调的核心价值：

- **格式控制**：严格按指定格式输出（JSON、表格、代码等）
- **领域适配**：注入行业知识和专业术语
- **风格统一**：保持一致的语气和回答模式
- **成本降低**：微调后的小模型可以替代大模型 API 调用
- **隐私保护**：本地部署，数据不出门

## 3. 微调技术分类

### 3.1 按参数更新范围分类

```
微调技术
├── 全量微调（Full Fine-tuning）
│   └── 更新模型所有参数
├── 参数高效微调（PEFT）
│   ├── LoRA / QLoRA    ← 最主流
│   ├── Adapter
│   ├── Prefix Tuning
│   └── Prompt Tuning
└── 对齐微调
    ├── SFT（监督微调）
    ├── RLHF（人类反馈强化学习）
    └── DPO（直接偏好优化）
```

### 3.2 全量微调 vs 参数高效微调

| 维度 | 全量微调 | LoRA/QLoRA |
|------|---------|------------|
| 可训练参数 | 100%（数十亿） | 0.1%~1%（数百万） |
| 显存需求 | 7B 模型需 ~80GB | 7B 模型需 ~16GB（QLoRA 可降至 ~6GB） |
| 训练速度 | 慢 | 快 3~10 倍 |
| 效果 | 理论上限最高 | 接近全量微调（通常 95%+ 效果） |
| 适用场景 | 领域差异极大 | 大多数场景 |
| 推荐度 | 除非必要，不推荐 | **强烈推荐** |

<img src="/images/finetuning/lora-principle.svg" alt="LoRA 原理：低秩分解" style="max-width:100%;margin:1.5em 0;" />

### 3.3 LoRA 原理（一分钟版）

LoRA 的核心思想极其简洁：

> 模型的权重矩阵 W 很大（比如 4096x4096），但微调时实际需要更新的「方向」很少。所以我们不直接改 W，而是加一个低秩分解 W + BA，其中 B 和 A 是两个很小的矩阵。

```
原始：y = Wx
LoRA：y = Wx + BAx

其中：
  W: 4096 × 4096（冻结，不训练）
  B: 4096 × r   （可训练）
  A: r × 4096   （可训练）
  r: 秩，通常 8~64
```

打个比方：全量微调就像重新粉刷整面墙（改 W），LoRA 就像在墙上贴几张便利贴（加 BA）——效果差不多，但工程量天差地别。

### 3.4 主流 PEFT 方法对比

| 方法 | 原理 | 优势 | 劣势 |
|------|------|------|------|
| **LoRA** | 低秩矩阵分解 | 效果好、通用性强 | 需要选择 r 和 target_modules |
| **QLoRA** | LoRA + 4bit 量化 | 极低显存 | 训练稍慢 |
| **Adapter** | 在层间插入小网络 | 理论优雅 | 推理有额外延迟 |
| **Prefix Tuning** | 在输入前加可学习前缀 | 不改模型结构 | 效果一般 |
| **Prompt Tuning** | 只优化 soft prompt | 参数最少 | 效果有限 |

> **实践建议**：95% 的场景直接用 LoRA 或 QLoRA，不需要纠结其他方法。

## 4. 微调 vs Prompt Engineering vs RAG

这是最常见的选型困惑。三者不是互斥的，而是互补的。

### 4.1 三种方案对比

| 维度 | Prompt Engineering | RAG | 微调 |
|------|-------------------|-----|------|
| 核心思路 | 优化提示词 | 检索外部知识 | 改变模型参数 |
| 实现难度 | 低 | 中 | 高 |
| 知识更新 | 改提示词即可 | 更新知识库 | 需重新训练 |
| 适合场景 | 通用任务调整 | 知识密集型问答 | 行为模式改变 |
| 成本 | 接近零 | 中（向量数据库） | 高（GPU 训练） |
| 延迟 | 无额外延迟 | 检索增加延迟 | 无额外延迟 |

### 4.2 决策流程图

```
你的需求是什么？
│
├─ 只是调整输出格式/风格？
│  └─ → Prompt Engineering（先试这个）
│
├─ 需要最新/私有知识？
│  └─ → RAG（检索增强生成）
│
├─ 需要模型「本能地」掌握某种能力？
│  ├─ 训练数据 < 100 条？ → Prompt Engineering + Few-shot
│  ├─ 训练数据 100~10000 条？ → LoRA/QLoRA 微调
│  └─ 训练数据 > 10000 条？ → 全量微调（如有资源）
│
└─ 以上都需要？
   └─ → 微调 + RAG 组合（最佳实践）
```

### 4.3 组合使用的最佳实践

最强的方案是**三者组合**：

1. **微调**：让模型学会你的输出格式和基本领域知识
2. **RAG**：补充实时、可更新的知识
3. **Prompt Engineering**：在推理时进一步控制行为

```
用户提问
  ↓
[Prompt Engineering] 构建系统提示词
  ↓
[RAG] 检索相关文档片段
  ↓
[微调模型] 生成回答（已内化格式和领域知识）
  ↓
结构化输出
```

## 5. 微调的完整流程

### 5.1 端到端工作流

```
1. 明确目标          → 你要模型做什么？
2. 选择基座模型      → Qwen2.5、Llama3、Mistral...
3. 准备训练数据      → 收集、清洗、格式化
4. 选择微调方法      → 通常 LoRA/QLoRA
5. 配置训练参数      → 学习率、batch size、epochs...
6. 训练              → 使用 Hugging Face Transformers + PEFT
7. 评估              → 自动指标 + 人工评测
8. 合并与部署        → 合并权重 → 量化 → 部署
9. 持续迭代          → 收集反馈 → 改进数据 → 重新训练
```

### 5.2 基座模型选择指南

| 模型 | 参数量 | 适用场景 | 推荐度 |
|------|--------|---------|-------|
| **Qwen2.5** | 0.5B~72B | 中文场景首选 | ★★★★★ |
| **Llama 3.1** | 8B~405B | 英文/多语言 | ★★★★★ |
| **Mistral** | 7B | 欧洲合规场景 | ★★★★ |
| **Gemma 2** | 2B~27B | 轻量级部署 | ★★★★ |
| **Yi** | 6B~34B | 中文场景备选 | ★★★ |

> **选择建议**：
> - 中文业务 → Qwen2.5-7B 或 Qwen2.5-14B
> - 英文业务 → Llama-3.1-8B
> - 资源受限 → Qwen2.5-1.5B 或 Gemma-2-2B

## 6. 常见误区

### 误区 1：微调 = 让模型「记住」知识

微调更多是改变模型的**行为模式**，而不是灌入知识。如果你想让模型掌握特定知识，RAG 通常更合适。

### 误区 2：数据越多越好

质量远比数量重要。1000 条高质量的指令数据，通常优于 10000 条低质量数据。

### 误区 3：微调很贵

使用 QLoRA，一张消费级 GPU（RTX 4090, 24GB）就能微调 7B 模型。云服务器成本也很低（阿里云 A10 约 10 元/小时）。

### 误区 4：微调一次就够了

微调是一个持续迭代的过程。第一次微调通常只是起点，你需要根据评估结果不断改进数据和参数。

## 7. 小结与下一步

### 本文要点

1. 微调是在预训练模型上用任务数据继续训练
2. LoRA/QLoRA 是当前最推荐的微调方法
3. 微调、RAG、Prompt Engineering 三者互补，不是互斥
4. 选择合适的基座模型很关键
5. 数据质量 > 数据数量
